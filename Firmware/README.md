# STM32H745 dual-core firmware — Stage 1 foundation

**Status: Stage 1 generated and independently rebuilt for CM7 and CM4, each with 0 errors and 0 warnings (2026-10-12).**

See **[Stage 1 engineering report](STAGE1_DUAL_CORE_FOUNDATION.md)** for detailed design rationale, generated configuration audit, reproducibility evidence, limits, and Stage 2 handoff. Firmware builds do **not** establish hardware execution or physical IPC correctness.

## Authoritative generator

Use STM32CubeMX/STM32CubeIDE to generate two independent firmware images from
one H745 device configuration. Do **not** hand-write/resettable-copy startup
vectors, linker files, clock setup, or ST HAL drivers.

- MCU family: STM32H745II. **Verify the exact suffix/package with the team**
  (for example STM32H745IIT6 is LQFP176; STM32H745IIK6 is UFBGA).
  A temporary MCU selection does not validate PCB pins or final procurement.
- Firmware package: STM32Cube_FW_H7_V1.13.0, already installed on the team's PC.
- Language: C; target: STM32CubeIDE / STM32Cube-managed executable.
- Two separate core contexts: CM7 and CM4, each with its own FreeRTOS instance,
  static configuration, startup, linker script, vector table, and build.
- System clocks, HAL configuration and core boot scaffolding: generated by ST.
- Keep the generator's .ioc file under version control.
- No CAN, NOR/QSPI, GPIO, UART/physical HMI, custom IPC, or pin assignments yet.
  Those belong in later integration stages after the board decisions.

## Planned application ownership

| CM7 | CM4 | Cross-core |
| --- | --- | --- |
| Supervisor, CANopen, 500 Hz trajectory consumer, motion control | External flash worker, 256-sample trajectory producer, modular HMI service | Two FreeRTOS Message Buffers, HSEM notifications, SRAM4 |

**Important:** The host repository's root `FreeRTOSConfig.h` is a POSIX
simulation config, **not** a generated firmware config. Each core must have
its own target FreeRTOSConfig.h from CubeMX. Do not reuse the host config.

## Generation handoff

1. In the installed workflow, open standalone **STM32CubeMX** → New Project → MCU Selector; afterward open the generated project in STM32CubeIDE.
2. Choose the *correct, exact STM32H745II... order number* (select an H745
   dual-core **MCU**, not a specific evaluation board).
3. Set project name `GP_STM32H745`, language C, project type STM32Cube.
   Generate a single logical dual-core project with distinct CM7 and CM4
   IDE subprojects. Pin the MCU firmware library to H7 V1.13.0.
4. In the CubeMX Pinout & Configuration contexts, enable FreeRTOS for
   **both** CM7 and CM4. Keep ST's generated dual-core boot infrastructure.
   Do not add application code or own peripheral initialization yet.
5. In Project Manager / Code Generator, keep user code in user sections
   and generate peripheral/middleware init source as separate files where
   available. Use the STM32CubeIDE toolchain and choose Generate Under Root
   where available in standalone CubeMX.
6. Generate code and **build CM7 and CM4 separately** in STM32CubeIDE.
   Correct ST generator configuration problems, not by rewriting startup.
7. After BOTH core builds pass, transfer the entire generated tree
   (including .ioc, CM7, CM4, Common and necessary Drivers/Middlewares)
   into `Firmware/STM32H745/`. Keep all linked resources and relative paths
   intact. Commit only source/configuration; exclude Debug/Release binaries.

### Not covered by Stage 1

ST firmware startup execution, boot handshakes, HSEM integration,
non-cacheable SRAM4 linker/MPU placement, and linking real robot application
modules are later stages; physical operation is not claimed by a build.

## Stage 2 — shared SRAM4 and MPU

See [Stage 2 design/audit log](STAGE2_SHARED_SRAM4_MPU.md).
First run `bash Firmware/Tests/check_shared_layout.sh` to establish
actual CM7/CM4 shared-object sizes using the generated FreeRTOS 10.6.2 headers.
Do not edit linker maps until this audit passes.

### Stage 2C linker validation (no MCU hardware)

`bash Firmware/Tests/check_sram4_linkers.sh` cross-compiles synthetic typed
shared objects against the vendored FreeRTOS 10.6.2 configuration for each
core, then links them using **each of the four** CubeIDE FLASH/RAM linker
scripts. It verifies fixed SRAM4 symbols, dedicated partitions and NOLOAD
sections. This does **not** replace complete CM7/CM4 CubeIDE firmware builds
or real MPU/cache-coherency tests. Re-run after any CubeMX regeneration.

### Stage 2D/2E firmware integration status

- **2A/2B:** ARM ABI and shared-memory capacity test passed with both cores'
  vendored FreeRTOS 10.6.2 headers.
- **2C:** SRAM4 slot address and `NOLOAD` tests passed for CM7/CM4
  FLASH/RAM linkers. Both baseline CubeIDE images were clean-rebuilt.
- **2D:** CubeMX-generated M7 Region 1 configuration for
  `0x38000000..0x38007FFF` (normal, shareable, non-cacheable,
  non-executable) committed; both firmware builds passed. Actual caches
  are currently disabled, and hardware MPU effects remain unverified.
- **2E (in progress):** adopt ST's official STM32H745
  `FreeRTOS_AMP_Dual_RTOS` example: M7 creates static shared Message
  Buffers **before releasing M4 through HSEM-0**, M4 verifies them, and
  ST's FreeRTOS/EXTI completion pattern notifies the peer. The obsolete
  `configUSE_STREAM_BUFFERS` guard and probe-only shims were removed;
  production object placement and boot/notification wiring are pending.
